# Write issue

An issue is a **contract** with whoever picks it up, often weeks later: what is
wrong or wanted, how to tell it is done, and where it stops. It states the
outcome and the boundaries. The implementation belongs to the plan, which reads
the code fresh at pickup.

Two branches: **write** files new issues (below); **upkeep** audits, rewrites and
closes existing ones ([UPKEEP.md](UPKEEP.md)). Both follow the body rules.

## Board notes

Read `<repo>/.claude/write-issue/board.md` first. It names the project number,
how a title scope maps to the App field, which labels to apply, the repo's
glossary and decision records, and any assumption in flux for an app. Without that file, ask the human for the board
before publishing anything.

## Body rules

- Start every body and comment you write with `> *This was generated by AI.*`
- **Behaviour, not code.** Leave out file paths, function names, SQL, schemas,
  model IDs and build steps: the code moves before pickup, and the plan decides
  them. Name a specific thing only when it *is* the decision ("reuse the stored
  performance band", "bundle id `io.subhan.content`") or the subject (the flaky
  spec file).
- **One real example** of the problem: the bad output quoted, the error, the URL.
- **Done-when criteria** are observable from outside: what a user, a test or a
  query sees. Each is checkable on its own. They replace a build list; never write
  both.
- **Evidence behind a link.** Eval results, cost workings, experiment tables and
  research notes go in a report, a PR or a comment. The body keeps only the
  numbers that drive the decision. Link a file on an unmerged branch at its commit
  SHA, so the link survives the branch.
- **No state in the body.** No "Type: AFK" lines and no progress logs: Type,
  Execution, Status and labels carry state, and comments carry history. A
  `<!-- ship-epic:status -->` block belongs to ship-epic; leave it while the epic
  is running.
- **Budget:** about 100 to 250 words, up to 450 for an epic. Past that, the body
  is carrying evidence or implementation, or it is two issues.
- Plain, direct statements. A literal phrase over a figure of speech.

## Kinds

| Kind | Type | Title prefix | Shape |
| --- | --- | --- | --- |
| feature | Feature | `feat` | Problem or Goal, Done when, Out of scope |
| bug | Bug | `fix` | Problem with a repro, Done when |
| task | Task | `chore`, `perf`, `refactor`, `test`, `docs` | Goal, Done when |
| research, spike | Task | `research`, `spike` | Question, Known so far, Done when |
| epic | Epic | the outcome's prefix, title ends `(epic)` | Outcome, Decisions, Children, Done when |

Templates and worked examples: [SHAPES.md](SHAPES.md). Titles are
`<prefix>(<scope>): <lower-case outcome>`, with the scope taken from board notes.

**Research never shares an issue with build work.** A research issue is done when
its decision is recorded, not when related code ships, so closing the build half
never closes open research. In an epic, research is its own child.

## Write

1. **Find existing work.** Search open and recently closed issues and merged PRs
   for the same work (`gh search issues`, `gh pr list --state merged --search`).
   When an open issue covers it, take the upkeep branch on that issue instead.
   When a merged PR already did it, tell the human. Done when you can name the
   closest issue and PR, or state that none exist.
2. **Check the parent and the assumptions.** For a sub-issue, the parent must be
   open, and its decisions must still hold for this child; a closed parent drops
   its children off the board's app views. List what the issue assumes (the
   tenancy model, a pending decision, an epic's contract, a provider) and check
   each against board notes and the glossary and decision records they name.
   An assumption a planned change will break is stated in the body, or the issue
   waits for that change.
3. **Draft.** Write the body in its kind's shape. Propose the fields: Type, App,
   parent, Execution (Agent, Human or Either), Priority, Size, and the state
   label. The state label is `needs-triage` unless the draft is fully decided:
   then `ready-for-human`, or `ready-for-agent` proposed.
4. **Review — gate.** Show the human each title, body and its fields together; a
   batch as a numbered list. Apply what they approve. `ready-for-agent` goes on
   an issue only when the human approves it for that issue by number: unattended
   agents start work on that label.
5. **Publish.** Blockers first, so "Blocked by" names real numbers.

   ```sh
   gh issue create --repo <repo> --title "<title>" --body-file <file> --label <labels>
   scripts/issue-fields.sh --repo <repo> --project <n> --issue <new> \
     --type <Type> --app <App> [--execution ..] [--priority ..] [--size ..] \
     [--status Backlog] [--parent <n>]
   ```

   The script prints the fields it reads back. Exit 1 means a value did not
   stick: report which. Done when every published issue's read-back line matches
   what the human approved.

## Called by another skill

When `to-issues`, `triage`, `port-journey`, `ship-issue` or `ship-epic` hands
you issues, the caller owns the breakdown; this skill owns the body, the fields
and publishing. Body content the caller requires (port-journey's design
snapshot) stays in; the body rules govern the rest. Run steps 1 to 5. The caller's own gate counts as step 4 when the
human saw the drafted bodies and fields there.
